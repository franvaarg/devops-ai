# Database safety

Use PostgreSQL 16+ with a dedicated application role and separate migration/backup credentials. Hosted DATABASE_URL connections force verified TLS and hostname validation. DB_* is for a trusted local/internal connection; use provider-supported verified TLS for external production connections. Pool defaults are 10 connections per instance, five-second connection acquisition and 15-second statement timeout. Account locks have bounded lock_timeout. Size total connections against the managed database limit before scaling.

`init.sql` creates a fresh schema. Migrations 001–005 are forward-only, additive and rerunnable. Never execute init/seed/drop/reset operations against an existing production database. No application startup migration or seed operation is enabled.

004 adds analysis decision JSON, billing cancellation/checkout columns, billing-event deduplication and anonymous event storage. It neither deletes nor rewrites user history/usage. It is now enclosed in BEGIN/COMMIT. 005 adds `(user_id,id DESC)` for owner-scoped history pagination and a partial analysis-request reference index to avoid scans during deletion. Normal index creation can block writes on large tables; prebuild the exact indexes CONCURRENTLY outside a transaction or use a maintenance window after staging measurements. Do not run concurrent index commands inside these transaction files.

Foreign keys cascade account deletion through history, usage, requests and password-reset tokens. Deleting an analysis nulls its request reference and preserves consumed usage; replay then returns not found. Product events have a nullable user FK and the application currently writes them without identity. Billing-event IDs intentionally retain no raw payment payload. Analyses retain redacted logs and context until deletion; there is no automatic age-based retention. No user-content migration is required for the new trust/provenance fields stored in decision JSON.

New setup: initialize only an empty database, then apply migrations in order. Existing setup: back up, restore into isolated staging, review SQL and apply `cd backend && npm run migrate -- --apply` with the intended migration environment. The CLI takes a session advisory lock, applies checked-in migrations, and records SHA-256 checksums in schema_migrations. Its first run on an existing database replays all additive migrations before recording them. If a prior ledger exists with different hashes, stop for operator review. Never overwrite checksums to suppress a mismatch. Migration files include their own transactions; a crash after DDL commit but before ledger insertion is recovered by safe reapplication.

Migration CLI needs the repository's `database/migrations` directory. The runtime-only backend Docker image does not contain it; run migrations from a reviewed repository checkout with installed backend dependencies. Production should not grant runtime DDL privileges.

Verification uses a freshly initialized private Unix-socket PostgreSQL cluster created by the test process. It ignores DATABASE_URL and refuses arbitrary database targets. Tests exercise concurrent quota admission/completion, replay, API ownership, signed webhook transactions, reset-token revocation, deletion, migration reapplication and preservation. These are local tests, not production backup/restore verification. See BACKUP_RESTORE.md.
